- [x] dynavlan C1 mechanism: Can `netplan try` be driven non-interactively from a script on a headless box (no TTY)? (resolved 2026-07-14 on the lab box) - YES, both paths work over SSH with no TTY: (1) unchanged config + no input -> counts down --timeout and reverts, exit 0; (2) feed newline to stdin -> "Configuration accepted.", exits immediately, no revert. So dynavlan's rollback = write 90-dynavlan.yaml -> `netplan try --timeout N` (applies then waits) -> health check (default route via base uplink present + reachability) -> feed "\n" to ACCEPT if healthy, else let timer REVERT. Timer also backstops script death mid-window. Impl detail for build: drive netplan try's stdin via a fifo/coproc so the accept can be sent after the health check.

- [ ] dynavlan C4 (original): Do the Protectli Intel NICs strip 802.1Q tags via rx-vlan offload before tcpdump sees them? (resolved 2026-07-14) - NO on this igb box: rx-vlan-offload already off. Tag stripping is not the problem here; tag filtering (C4b above) is the real risk. - architect says likely yes on Intel, which would make passive sniff detect zero VLANs. Test order on real hardware: (1) FIRST check whether `tcpdump -e -nn` already shows "vlan N" with offload left ON - Linux libpcap reconstructs the outer tag from PACKET_AUXDATA even when HW strips it, so we may not need to touch offload at all. (2) ONLY if tags are invisible, fall back to `ethtool -K <iface> rxvlan off`. Caveats for the fallback: ethtool -K can bounce the Intel link (igb/e1000e/igc reinit), and that interface carries Domotz's own untagged uplink, so it would briefly disconnect Domotz; the setting is runtime-only (re-apply per boot); apply ONCE at boot with check-then-set (query `ethtool -k` first, skip if already off), NEVER on the 5-min rescan (would bounce the uplink every cycle).

- [ ] dynavlan positioning: monitoring provisioner vs general-purpose dynamic-VLAN utility - does isolation-by-default match user expectation? (status: open, raised 2026-07-27) - The name "dynamic VLAN detection/enabling utility" reads general-purpose, but the behavior is monitoring-specific: every discovered VLAN comes up DHCP address-only with routes/DNS/NTP/domains declined (use-routes:false + accept-ra:false). That OVERRIDES netplan's own default (dhcp4:true accepts routes), so relative to the platform baseline dynavlan is the surprising one, and "enable a VLAN" in plain usage implies a routable interface. Tension: many users would EXPECT routable VLANs, BUT the naive "routes on all VLANs" does not deliver "all routable" - it installs N competing default routes where only the lowest metric is used, plus DNS/NTP pollution and asymmetric routing (observed in the 2026-07-27 drill: 7 defaults, uplink metric 10 carried everything, 100-106 inert). So meeting the expectation naively produces a footgun that scales badly, which is WHY monitoring/appliance tools isolate, and why the FR-18 health-check safety model DEPENDS on VLANs installing no default route. Resolution direction (NOT a default flip): this is a positioning problem, not a default-value problem. Keep isolation the engineering default; fix expectations at the framing layer - README/PRD lean explicitly into "isolated monitoring provisioning, routed is opt-in", and/or make the choice EXPLICIT at install (monitor mode vs routed mode) so the user picks their mental model. Deeper decision underneath: is the product a monitoring tool (PRD's current scope) or a general dynamic-VLAN tool? The default falls out of that. If general-purpose "test routing on all VLANs" is ever a real target, the right feature is per-VLAN source-based reachability testing (probe each VLAN's gateway, report reachable/not, DON'T touch the main table) - a NEW capability, not VLAN_ROUTES=true. Next step: operator decides product identity; until then, DOCUMENT clearly (done 2026-07-27: README + deployment-guide made explicit about isolation default and how to enable routed mode). No code/default change without a concrete second use case (YAGNI).
