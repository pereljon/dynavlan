- [x] dynavlan C1 mechanism: Can `netplan try` be driven non-interactively from a script on a headless box (no TTY)? (resolved 2026-07-14 on the lab box) - YES, both paths work over SSH with no TTY: (1) unchanged config + no input -> counts down --timeout and reverts, exit 0; (2) feed newline to stdin -> "Configuration accepted.", exits immediately, no revert. So dynavlan's rollback = write 90-dynavlan.yaml -> `netplan try --timeout N` (applies then waits) -> health check (default route via base uplink present + reachability) -> feed "\n" to ACCEPT if healthy, else let timer REVERT. Timer also backstops script death mid-window. Impl detail for build: drive netplan try's stdin via a fifo/coproc so the accept can be sent after the health check.

- [ ] dynavlan C4 (original): Do the Protectli Intel NICs strip 802.1Q tags via rx-vlan offload before tcpdump sees them? (resolved 2026-07-14) - NO on this igb box: rx-vlan-offload already off. Tag stripping is not the problem here; tag filtering (C4b above) is the real risk. - architect says likely yes on Intel, which would make passive sniff detect zero VLANs. Test order on real hardware: (1) FIRST check whether `tcpdump -e -nn` already shows "vlan N" with offload left ON - Linux libpcap reconstructs the outer tag from PACKET_AUXDATA even when HW strips it, so we may not need to touch offload at all. (2) ONLY if tags are invisible, fall back to `ethtool -K <iface> rxvlan off`. Caveats for the fallback: ethtool -K can bounce the Intel link (igb/e1000e/igc reinit), and that interface carries Domotz's own untagged uplink, so it would briefly disconnect Domotz; the setting is runtime-only (re-apply per boot); apply ONCE at boot with check-then-set (query `ethtool -k` first, skip if already off), NEVER on the 5-min rescan (would bounce the uplink every cycle).

- [x] dynavlan positioning: monitoring provisioner vs general-purpose dynamic-VLAN utility - does isolation-by-default match user expectation? (resolved 2026-07-29) - RESOLVED per the operator steer below: dynavlan is now positioned as a GENERAL dynamic-VLAN provisioner with a monitoring origin, not a monitoring-only tool. Isolation stays the DEFAULT (unchanged - still the safe engineering choice, and FR-18's health-check model still depends on it), but routed mode is presented as a first-class supported configuration rather than a niche exception. README/PRD/deployment-guide reframed accordingly on 2026-07-29, landing in the same pass as the all-trunks (v0.2.0) implementation. This is a framing change only; no default or behavior changed as a result of this resolution. The original tension (many users expect "enable a VLAN" to mean routable, but naively routing every VLAN produces a footgun - N competing default routes, DNS/NTP pollution) still holds and is still why isolation is the engineering default; the resolution is that the STORY no longer leans on "this is a monitoring appliance" to justify it, since the tool is general-purpose and isolation is independently the right default for any tool auto-adding many interfaces to a box's routing table.

- [ ] dynavlan FR-41: does the minimal two-sample carrier-down debounce cause remove-then-re-add churn in the field, or is the deferred grace-timer alternative unnecessary? (status: open, blocked on field data) - the chosen debounce (two samples a `BOOT_SETTLE_SECONDS` settle apart, in-run, no persisted state) accepts a monitoring-agent restart if a trunk's outage (switch reboot, cable re-patch) outlasts the settle but is still meant to be transient - the trunk gets pruned, then re-added on the next cycle once it recovers. The deferred alternative (a persistent `/run` tracker requiring continuous down-ness for ~2 rescan cycles before pruning, `context/decisions.md` 2026-08-03) would avoid that churn at the cost of an ephemeral state file and a new grace config knob, and ~10 minutes slower cleanup of a genuine unplug. Revisit only once there is real field evidence (a box hardware-validated and running for a while) that switch-maintenance windows or cable work actually trigger this churn in practice - not before.
