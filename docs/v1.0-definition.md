# dynavlan 1.0 definition

Status: approved. This is the authoritative, tracked 1.0 definition. Live gate
status lives in `context/todo.md`; the decision record is `context/decisions.md`
(2026-08-03). Originated from the brainstorm design note
`docs/superpowers/specs/2026-08-03-v1.0-definition-design.md` (working notes,
local-only); the authoritative content was relocated here so it is version-tracked.

## Purpose

Define what tagging dynavlan **1.0** means: the maturity bar the release must
clear, the gates that must ship first, the compatibility promise 1.0 obligates
for the whole 1.x line, and what is explicitly out of scope. The compatibility
policy below graduates into `COMPATIBILITY.md` when the final gate lands.

## What 1.0 signifies

A blend of maturity signals, not a marketing tag:

- **Feature-complete VLAN lifecycle** -- discover, add, *and* remove.
- **Hardened distribution** -- apt-upgradable from a signed repo, not just a
  one-shot install script.
- **Proven beyond the reference lab** -- validated on a second independent
  deployment, on a non-Meraki switch.
- **A stated compatibility contract** -- the config surface carries a written,
  enforceable promise about how it can change within 1.x.

1.0 is an engineering maturity bar. It does not commit to a docs site, rebrand,
or pricing model (those remain open positioning questions, tracked separately in
`docs/positioning-brief.md`).

## Release gates

All four must be met before the 1.0.0 tag. They are different kinds of work and
reach the tag by different paths (see Version path).

### Gate 1 -- Carrier-down VLAN removal (v0.4.0)

The existing approved design executed, code-reviewed, and hardware-validated on
the reference box.

- Design: `docs/superpowers/specs/2026-07-30-carrier-down-vlan-removal-design.md`
- Behavior: prune on sustained carrier loss (two-pass within a `--boot` run);
  carrier-up-no-tags still preserved; new `REMOVE_ON_CARRIER_LOSS` knob, default
  true, independent of `RESET_ON_BOOT`.

Acceptance: released and tagged v0.4.0, unit suite green, minor-release code
review clean, hardware-validated on the reference box (prune fires on sustained
carrier loss; a cable pull that returns before the second pass does not remove).

### Gate 2 -- APT distribution

A box can pick up new dynavlan versions with `apt-get update && apt-get upgrade`
from a signed repository.

- Design: `docs/superpowers/specs/2026-08-03-apt-repository-hosting-design.md`
- Approach: GitHub Pages + reprepro, public, manual/attended upgrades only
  (explicitly **not** unattended-upgrades).

Acceptance: repo published and signed; the reference box actually upgrades
dynavlan via apt, console-backed; `get.sh` is apt-aware with a tarball fallback;
offline signing-key backup + revocation certificate exist before first publish;
Pages source set to "GitHub Actions".

### Gate 3 -- Second-box / multi-site validation

Prove the tool on an independent deployment, not just the reference box.

- The **non-Meraki switch** requirement is **already satisfied**: the v0.3.0
  hardware validation (2026-07-30) ran detection + provisioning on a **UniFi
  trunk** (`context/index.md`; test L3-33 "UniFi and Meraki"). UniFi/Ubiquiti is
  a distinct vendor from Meraki, so sniff-primary detection is proven off Meraki.
- Remaining work: detection + apply/revert exercised, console-backed, on **at
  least one additional physical box at a different site**.

Acceptance: a second physical box at a different site boots, detects its
trunk(s), provisions VLANs, and survives the apply/revert path console-backed;
any defects that surface are fixed and ride a patch (v0.4.z); recorded as a
validation record. This gate is about a second independent deployment, not a
second switch vendor.

### Gate 4 -- Config-surface freeze + compatibility policy

The release whose tag is **1.0.0**. Its content is the stability contract, not a
code feature.

- **Enumerate the stable surface**: config keys, generated `90-dynavlan.yaml`
  shape, CLI flags, and exit codes.
- **Publish the compatibility policy** (below) in `COMPATIBILITY.md`,
  cross-linked from the README.
- **Implement the version-gate git hooks** (previously "designed but not built",
  `context/todo.md`) so the FR-38 version/build identity contract cannot silently
  decay (pre-commit enforcement of the `ver=` bump gate and the `build=` column-0
  invariant that `tests/unit.sh` §1l already checks).

Acceptance: `COMPATIBILITY.md` published and cross-linked; the stable surface
enumerated in it; git hooks installed and demonstrated to block a commit that
violates the version/build identity contract; 1.0.0 tagged and released on
`pereljon/dynavlan`.

## Compatibility policy (deprecate-with-warning)

The promise 1.0 makes for the entire 1.x line. Chosen over semver-strict to let
the config surface still evolve during 1.x, at the cost of a two-step process for
any break.

Scope of the promise: config keys (names, accepted values, defaults), the
generated `90-dynavlan.yaml` shape, CLI flags, and exit codes.

- **Additions are always free in a minor.** New config keys that default to
  current behavior, new CLI flags, and new log lines may land in any 1.x minor
  without a deprecation cycle.
- **Breaking changes ship in two steps, never one.** A "breaking" change is:
  removing or repurposing a config key, removing a CLI flag, changing a default
  in a way that alters behavior on an existing box, changing an exit code's
  meaning, or changing the generated YAML in a way that breaks the owned-set
  round-trip or an external consumer. Such a change requires:
  1. A release that emits a **deprecation warning** on the old form. The old form
     still works and produces the same behavior. The warning names the
     replacement and links the migration note.
  2. A **later** release (never the same one) that removes or changes it.
- **2.0 is reserved** for changes that cannot be done via the two-step path.

Enforcement: the compatibility policy is documentation + review discipline; the
FR-38 version-identity git hooks (Gate 4) make the version bump that signals
these changes non-optional.

## Explicitly out of scope for 1.0 (documented limitations)

Each is recorded as a stated limitation in the shipping docs, not silently
absent:

- **IPv6.** 1.0 provisions IPv4 only; the FR-14a IPv6 health-check arm stays
  deferred. IPv6 (dhcp6/SLAAC provisioning + the health-check arm) is a post-1.0
  workstream. This is the one notable capability boundary and must be stated
  plainly in README/PRD.
- **Exhaustive vendor coverage.** 1.0 validates one non-Meraki vendor (UniFi),
  not a broad matrix. Cisco Catalyst/Nexus, Aruba, Juniper, HP/Comware LLDP
  VLAN-table advertisement and silent low-traffic-VLAN gaps remain post-1.0
  (tracked in `context/open_questions.md`).
- **`PER_VLAN_MAC`** is a reserved, unimplemented key in 1.0: default off, and
  `load_config` hard-refuses `true` (FR-15). A per-VLAN MAC derivation is a
  post-1.0 item (G-4).
- **Automatic config-drift detection** on boot/rescan stays deferred.

## Version path

The path to 1.0.0:

1. **v0.4.0** -- merge and release carrier-down removal (Gate 1). Real `ver=`
   bump (script feature).
2. **APT distribution** (Gate 2) -- packaging + `get.sh` + release workflow.
   Touches the `dynavlan` script's `ver=` only if the script itself changes; per
   the APT design it does not, so **no `ver=` bump** unless incidental.
3. **Second-box / multi-site validation** (Gate 3) -- evidence workstream. Any
   fixes ride a patch (v0.4.z).
4. **v1.0.0** -- the config-surface freeze, `COMPATIBILITY.md`, and version-gate
   git hooks (Gate 4). Tag 1.0.0 once Gates 1-3 are cleared and the freeze
   artifacts land.

Gates 2 and 3 can proceed in parallel; both are independent of the v0.4.0
release. Gate 4 is last by construction: the surface is frozen only after the
features that shape it (Gate 1) have shipped.

Rejected alternative -- **big-bang 1.0** (hold all four gates on a branch, tag
1.0.0 in one shot): gives up per-milestone hardware validation and contradicts
the project's "never strand, release each validated milestone" cadence, which the
deprecate-with-warning promise also depends on (incremental releases are where a
deprecation warning gets a chance to ship before the removal).

## Review and refactoring cadence

- **Refactoring:** no dedicated refactor pass. `dynavlan` is single-file by
  design and the apply/rollback state machine is deliberately coupled
  (CLAUDE.md); refactor opportunistically as gate work touches a function. The
  Gate 4 freeze locks the **external** surface (keys, flags, YAML shape) only,
  not internal code layout, so internal refactors stay free even after 1.0. There
  is no "last chance to refactor before the freeze".
- **Per-release review:** v0.4.0 (Gate 1) gets the normal minor-release review
  (units added or modified), per CLAUDE.md "Code Review Before Release".
- **1.0.0 full review:** the major bump gets a **full review of the relevant
  surface** (apply / detection / removal), per the same policy. This is the
  major-release gate and lands as part of Gate 4, after the surface is final and
  before it is frozen.
- **Cross-model review:** run the 1.0.0 full review with **at least one non-Opus
  reviewer** (Fable and/or a GPT model), each briefed adversarially to hunt what
  prior reviews missed. Precedent: the 2026-07-23 review rounds, where a fresh
  Fable reviewer caught the CRITICAL fifo-ACCEPT race two prior Opus reviews had
  passed (`context/decisions.md`). `/code-review ultra` (multi-agent cloud
  review) is a further option for the major. Cheap insurance for a
  safety-critical apply path where a bad revert can strand a headless box.
