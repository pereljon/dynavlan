# Changelog

## Unreleased

- Added: `dynavlan --reapply` (FR-39). dynavlan rewrites its netplan file only when the VLAN *set* changes, so a change to what it GENERATES never reached a box whose VLANs were stable: FR-14a shipped this session, installed cleanly, and was provably inert on the validated box, which kept an RA-installed IPv6 default route through a monitored VLAN. `--reapply` regenerates the owned set with the running build and applies it only if the generated body actually differs from what is on disk, through the full `netplan try` + health-check chain. It runs NO detection (pinned to the owned parent - detecting could silently turn a reapply into a trunk relocation onto a different NIC), never adds or removes a VLAN, lease-waits the entire owned set before restarting targets (there are no additions to wait on, and restarting an interface-enumerating agent mid-re-DHCP would drop kept subnets), bypasses the count gate (`fill` mode would otherwise trim the owned set, turning a reapply into a silent removal), and blocks on the run lock rather than reporting a misleading rc-0 "skipped" to an operator. The comparison ignores exactly line 1, the version/build header, so an FR-38 build stamp change alone cannot force a no-change apply. Automatic drift detection on boot/rescan is deliberately not included: with one deployed box, the fleet-correlation risk that would justify it does not exist yet. Note the limitation: this compares files, so it proves file equality, never behavioral equality.
- Fixed: routed mode (FR-37) could only ever be enabled on a box that owned no VLANs yet. `apply_change` passed the ADDITIONS to `assign_route_metrics` as the set needing metrics, but the correct set is "target ids that do not already have one". Those differ exactly on an isolated -> routed migration: an operator setting `VLAN_ROUTES=true` on a box that already owns VLANs leaves every owned id without a metric while additions is empty or covers only a new VLAN, so `backend_generate_config` refused with `internal: no route metric assigned for VLAN N` - permanently, on every subsequent run, which also blocked adding any new VLAN until the setting was reverted. The `internal:` prefix compounded it by reading as a code defect rather than "unreachable from this state". Assignment now lives in one pure `plan_route_metrics` that every caller must use, so the apply path and any future preview path cannot diverge. No stranding risk: the refusal precedes `netplan try`, so live state was never touched. Found by an adversarial review of the FR-39 proposal, then reproduced against committed code.
- Fixed: `lldp_tagged_vlans` matched any key ending in `.vlan-id=` / `.pvid=yes` rather than the VLAN TLV's own `.vlan.` subtree (found in the 2026-07-25 review round). lldpd's full key set is undocumented, so the loose match made the parse depend on assuming what else it emits, and a foreign `.vlan-id=` key landing inside a VLAN block did two things: it flushed the real id as "tagged" before its `pvid=yes` was seen, rebuilding exactly the dead native-VLAN interface FR-7a exists to prevent, and it leaked the foreign key's own value as a VLAN candidate, so dynavlan would build an interface for a VLAN not on the trunk at all. Patterns now anchor on `.vlan.vlan-id=` / `.vlan.pvid=yes`; two regression cases added (tests 1i).
- Added: `dynavlan --version` (alias `-V`) and an install-stamped build identity (FR-38). Prints `dynavlan <ver> (build <commit>)` and exits before the config load and the root check, so it answers when the config is invalid or the caller is unprivileged - the cases where the question actually gets asked. `install.sh` stamps the source checkout's short commit into the script, suffixed `-dirty` when the tree had uncommitted changes, and warns at install time when it does; a non-git install stamps `unknown` rather than inventing an identity. The same string now appears on every `run start:` journal line and in the generated netplan file's header, making provenance recoverable from the journal alone. Motivated by a real misdiagnosis: a deploy that landed between two edits was read as a failed fix, because nothing on the box could distinguish the running code from the intended code. Semver cannot do this job - every build of an unreleased version self-reports identically.
- Fixed: VLANs accepted IPv6 Router Advertisements, so "fully route/DNS-isolated" was only ever true for IPv4 (FR-14a). The four `use-*: false` keys are `dhcp4-overrides` and bind DHCPv4 alone, while networkd accepts RAs by default on a non-router link: a VLAN could hand the box a SLAAC address, RDNSS resolvers, and a default route through a monitored subnet, none of it declined by any key we set. Worse than a leak, this broke a stated dependency of the rollback path, since the FR-18 health check samples IPv4 defaults only and could never see an RA-installed default, let alone revert one. Every generated VLAN now carries `accept-ra: false`, in routed mode as well as isolated (FR-37's guard reasons only about metrics dynavlan assigns; an RA route carries one it never chose). `link-local` is untouched, so `fe80` addresses remain. Found on hardware: `enp1s0.22` held a global SLAAC address with every DHCPv4 decline in force.
- Changed: `VLAN_MIN` default is now 1 (was 2). The old default encoded "VLAN 1 is the switch management VLAN" as if it were a fact about the wire; it is a convention, and a validated Meraki trunk broke it in both directions, carrying VLAN 1 tagged as a live DHCP subnet while the management/native VLAN was 100. A range-filtered ID is not reported as an exclusion, so the dropped subnet was invisible short of diffing `detected` against `owned` by eye. `VLAN_IGNORE` remains the way to skip specific IDs, including 1, where a site-specific management VLAN belongs.
- Fixed: detection counted the box's own transmitted frames, making it self-fulfilling (FR-5a). `tcpdump` captures egress as well as ingress, and every owned VLAN transmits tagged DHCP on the parent (DISCOVER retries forever if it never leases, renewals if it did), so an owned VLAN was permanently "detected" on nothing but its own traffic. FR-23 removal could therefore never fire - not for a VLAN created in error, nor for one the switch had genuinely stopped trunking. The sniff now uses `-Q in`, and missing `-Q` support is a refuse-to-run precondition rather than a silent fallback to bidirectional capture. Found on hardware: a dead `enp1s0.100` kept itself alive across reboots on 1 outbound DHCP Request from the box's own MAC, with 0 inbound frames in a 75s window.
- Fixed: the rescan timer never fired, on any install (FR-21a). `dynavlan --reconfigure` rendered a drop-in that cleared `OnUnitActiveSec` before re-setting it, but in systemd an empty assignment to any `On*Sec=` resets the *entire* monotonic timer list, so the base unit's `OnBootSec` first-fire trigger was silently discarded. That left the timer anchored solely on `OnUnitActiveSec`, which needs a previous activation of the rescan service to anchor on; with none it never elapsed. The timer reported `active` and `Result=success` the whole time, so nothing surfaced an error and periodic add-only discovery was simply absent. The drop-in now restates every trigger, using `OnActiveSec` (timer activation) so it also survives the stop/restart `install.sh` performs on upgrade. Found on hardware via `systemctl list-timers` showing `n/a` in every column.
- Fixed: `install.sh` could replace `/usr/local/sbin/dynavlan` underneath a running invocation. bash reads a script lazily by file offset, so an in-place rewrite during a live `--rescan` could execute garbage or stop mid-logic, possibly between `netplan try` and its confirmation. The installer now stops `dynavlan.timer` for the duration (restored on every exit path via a trap, including failures) and takes the FR-30 lock with `flock -w 300` before touching the script, refusing loudly rather than swapping under a live run. Also fixed a false claim in the closing message that the rescan timer was already active, which was untrue on a fresh install.
- Changed: install docs recommend `sudo bash install.sh` over `sudo ./install.sh`. Transfers that do not carry Unix modes (GitHub ZIP, `rsync` without `-p`) strip the executable bit; invoking the interpreter is immune. The mode of `dynavlan` itself is irrelevant, as the installer places it with `install -m 0755`.
- Fixed: LLDP detection ingested the native/pvid VLAN as if it were tagged (FR-7a). `lldpctl` flags the native VLAN `pvid=yes`, but the parse grepped every `vlan-id=` line and discarded the flag, so dynavlan built a VLAN interface for a tag that is untagged on the wire: it came up, never acquired a lease, and re-warned on every rescan. New pure helper `lldp_tagged_vlans` correlates each `vlan-id` with its adjacent `pvid` and drops the native VLAN; the exclusion is scoped to the LLDP source, so a VLAN the sniff independently sees tagged is still a candidate. Found on hardware (Meraki trunk advertising pvid 100; `enp1s0.100` took no lease).
- Fixed: the FR-0 netplan version precondition refused to run on every target box. It probed `netplan --version`, a flag that only exists on netplan >= 1.0, while the validated Ubuntu 22.04 baseline ships 0.10x and rejects it; the empty parse surfaced as the misleading `netplan >= 0.106 required (found unknown)`. Version discovery now falls back to `dpkg-query -W netplan.io`, and "cannot determine version" is logged as a refusal distinct from "version below the minimum". Found on hardware (netplan.io 0.107.1-3ubuntu0.22.04.4, Ubuntu 22.04).
- Changed: `RESTART_SNAPS` default is now empty (was `domotzpro-agent-publicstore`); the Domotz agent snap is the documented example, not a baked-in default. Set it explicitly per deployment.
- Removed: the Domotz-on-Ubuntu deployment runbook and base-deployment spec (`docs/deployment-guide.md` rewritten as the dynavlan deployment guide; `dev/IMPLEMENTATION-SPEC.md` deleted). The project is dynavlan; Domotz remains only as the restart-target example.

- Added: opt-in routed mode (FR-37): `VLAN_ROUTES=true` accepts DHCP routes on discovered VLANs at per-VLAN metrics; `VLAN_ROUTE_METRIC_START` (default 100) and `VLAN_ROUTE_METRIC_MODE` (`discovery` = order found, existing VLANs never renumber, persisted in the owned YAML; `id` = START + VLAN id, stateless). Refuses up front if any assigned metric would match or beat the uplink default's metric. DNS/NTP/domains stay declined in both modes. Default remains fully route-isolated.

- Fixed: `restore_prior` now checks its copy-back and logs `err` naming the surviving backup on failure (silent disk/live divergence on the revert path was possible under disk pressure) (round-4 review).
- Changed: `--dry-run` now takes the run lock non-blocking - holds it during the preview if free (a mid-preview timer rescan skips normally); warns and proceeds read-only if a run is already in progress (round-4 review).
